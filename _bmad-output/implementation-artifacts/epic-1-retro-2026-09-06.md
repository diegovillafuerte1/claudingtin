### Aggregate view — spec-to-implementation reconciliation

#### F1 — CI never runs `go test -race`; four separate story reviews deferred it as "repo-wide"
- **Source:** `.github/workflows/ci.yml:52-58` (the `test` step is a bare `go test`); `deferred-work.md` entries for `spec-1-1`, `spec-1-4`, `spec-1-5` (verification-gap layer, four entries). Specs 1.3 / 1.4 / 1.5 Verification sections require `go test -race`.
- **Detail:** Story 1.4 introduced the first genuinely concurrent code (the AD-8 single-writer hub); 1.6 added the wsclient goroutines; 1.3 the fsnotify tailer. `go test -race ./...` passes cleanly today (verified this session on all modules). The gap is only that nothing enforces it going forward, so a future data race regresses undetected.
- **Instance disposition:** **fix now** — one-line CI change (add `-race` to the `go test` step; weigh scoping to `ubuntu` + `macos` since `-race` needs a C toolchain and the Windows runner cost).
- **Prevention:** when *N* story specs each defer the same infrastructure item to "repo-wide, not this story", the epic's dedicated infra story (here 1.2) should own it, or it should become a standing action item on first deferral — not be re-deferred N times.

#### F2 — Epic AC "`modernc.org/sqlite` build+open check on Windows" is absent from CI
- **Source:** `epics.md` Story 1.2 AC ("all tests run — including a `modernc.org/sqlite` build+open check on Windows"); `spec-1-2:28,40` deliberately descopes it ("The Windows job is where the *future* `modernc.org/sqlite` build-and-open assertion will live; today it just runs the suite" / "No SQLite schema or `modernc.org/sqlite` dependency yet — Story 1.4 / Epic 4"). No `sqlite` / `modernc` reference anywhere in the tree (verified).
- **Instance disposition:** **accept as deferred** — there is nothing to check until the dependency exists.
- **Prevention / reconciliation (proposed):** amend the `epics.md` Story 1.2 AC to carry the deferral inline (e.g. "…— deferred to the story that first imports `modernc.org/sqlite`"), so a later retro or epic gate does not re-flag a met-as-intended criterion as a miss.

#### F3 — `ws://` cleartext to any host is silently accepted; the architecture mandates TLS/WSS for all traffic
- **Source:** `companion/main.go:145-153` (`resolve` accepts the `ws` scheme to any host, only rejecting non-`ws`/`wss`); `epic-1-context.md:27` ("All client↔server traffic is TLS/WSS"); `ARCHITECTURE-SPINE.md` Consistency Conventions. The account key travels in the `hello` frame — on a `ws://` non-loopback URL, in cleartext. Already logged in `deferred-work.md` (`spec-1-6`, blind-hunter) as needing "a deliberate warn-vs-refuse decision".
- **Instance disposition:** **defer** (already tracked) — but elevate from hygiene to safety-relevant: the account key is the user's whole identity and the spine's TLS/WSS line is an invariant, not a preference.
- **Prevention:** an invariant like "all traffic is TLS/WSS" needs either an enforcement AC in the story that builds the dialer (1.6) or an explicit, time-boxed carve-out for loopback dev.

#### F7 — The composed first-run experience for non-tmux users is a silent dead end
- **Source:** `plugin/cmd/session-start/spawn_unix.go:23` and `spawn_windows.go:28-30` (`cmd.Stdin = devNull` on the detached spawn); `plugin/cmd/session-start/launch.go:186-218` (no-tmux path: detached spawn, then one `placementHint` line to stdout); `launch.go:128-137` (the hint's own comment: "SessionStart stdout is folded into the model's context rather than shown in the user's terminal"); `companion/internal/safety/safety.go:246-266` (`Gate` reads one stdin line; EOF ⇒ `OutcomeDeclined`); `companion/internal/run/run.go:92-97` (`OutcomeDeclined` ⇒ inert, wait for signal); `README.md:82-85` (acknowledges the behaviour).
- **Detail:** outside tmux, the companion is spawned detached with `stdin = /dev/null`, so `safety.Gate` reads EOF on first run, declines, and the companion is permanently inert. The only pointer to the remedy — run `companion <transcript> "" ""` in a real terminal — is the README plus a hint line that, per its own code comment, reaches the model's context rather than the user's terminal. So a VS Code / JetBrains / plain-terminal / PowerShell user who installs the plugin sees no visible prompt and gets a companion that does nothing, with no user-facing cue about how to proceed. Each piece is individually spec-compliant and human-approved (no-TTY-probing was explicitly approved for 1.9; `/dev/null` stdin is correct for a detached daemon in 1.7); the **composition** was never evaluated against "what does a non-tmux user actually see on first run".
- **Instance disposition:** **defer to a product decision** — not a code defect to hot-fix. Candidate fixes: a user-visible first-run cue, a companion-menu accept path, or TTY-aware placement (spawn attached when a controlling terminal exists).
- **Prevention:** an epic that splits launch (1.7), placement (1.8), and the first-run gate (1.9) across three stories needs one story — or the retro — to own the end-to-end first-run walkthrough on each supported host (tmux, VS Code terminal, JetBrains terminal, bare terminal, PowerShell).

#### F8 — `plugin/bin/` is empty, so the launch path is unproven end-to-end and non-functional in a real install
- **Source:** `plugin/bin/.gitkeep` is the only tracked file under `plugin/bin/` (`git ls-files` verified); `launch.go:181-184` silently no-ops when the companion binary is absent/non-executable; `deferred-work.md` (`spec-1-7`) notes "`plugin/bin/` currently holds only `.gitkeep`" and that no CI guard checks launcher/companion completeness.
- **Detail:** Stories 1.7 / 1.8 acceptance ("resolves the platform companion binary via `${CLAUDE_PLUGIN_ROOT}`") is unit-tested with fakes but has never executed against real committed binaries, and cannot until Story 6.x's first release populates `plugin/bin/<os>-<arch>/`. The epic's headline outcome — a companion that launches from a plugin install and tracks think-time — cannot be exercised from an actual install today.
- **Instance disposition:** **defer** — this is by design (`spec-1-2`: binaries come from a release, `plugin/bin/` refresh is a manual reviewed commit).
- **Prevention:** a greenfield epic whose value depends on committed release artifacts should schedule **one** real end-to-end run (populate `plugin/bin/` locally, install the plugin, start a session) rather than defer all integration proof to the release epic. Recommend doing this before Epic 2 builds the chat surface on top.

#### F9 — `plugin/hooks/hooks.json` used the wrong hook schema; the plugin failed to load in Claude Code (found while executing F8)
- **Source:** `plugin/hooks/hooks.json` (top-level `SessionStart` key — the `settings.json` hook shape); `plugin/.claude-plugin/plugin.json` `"hooks": "./hooks/hooks.json"`; Claude Code 2.1.263 debug log: `Failed to load hooks from ./hooks/hooks.json for claudingtin: "hooks.json must have `hooks` … or `modules`"` → `Registered 0 hooks from 1 plugins`. Every official hook-using plugin (`ralph-loop`, `hookify`, `claude-security`) nests events under a top-level `"hooks"` object. Full record in `epic-1-e2e-proof-2026-09-06.md`.
- **Detail:** the `SessionStart` registration was never a working registration — Claude Code silently disabled the whole plugin. Story 1.7's acceptance ("when the `SessionStart` hook runs …") was unit-tested against the launcher's pure core but never against a real Claude Code, because `plugin/bin/` was empty (**F8**) so the plugin was never installed, and there was no test asserting the manifest schema. `spec-1-7`'s frozen I/O specified the wrong shape.
- **Instance disposition:** **fixed** — `hooks.json` moved to `{ "hooks": { "SessionStart": [...] } }`; redundant `hooks` key removed from `plugin.json`; `plugin/cmd/session-start/manifest_test.go` added as a regression guard; `spec-1-7` annotated. Verified end to end against a live Claude Code session (`Registered 1 hooks`, `SessionStart:startup success`, companion spawns + connects, `/status` → 1).
- **Prevention:** ship a manifest-schema test with any plugin manifest, and do the real install before calling the launch story done — a pure-core unit test cannot see a host-integration schema mismatch.
