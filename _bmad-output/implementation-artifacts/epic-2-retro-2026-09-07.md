#### F6 — `run.loop` can hang forever on `chat.Println` after the chat program has exited — reachable on every keyboard `leave`
- **Source:** `deferred-work.md:191-193` (spec-2-4, edge-case-hunter + blind-hunter); `run.go:568-591` (the `chatIntents` arm calls `chat.Println` gated only on `chat != nil`), `run.go:559-566` (the `chatSends` arm, same), `run.go:593-596` (the separate `<-chatDone` arm); `chatui.go:271-277` (`leave` key → `m.notify(IntentLeave)` non-blocking send into `chatIntents`, then `return m, tea.Quit`).
- **Detail:** on a keyboard `leave` (`ctrl+q`), `chatui` buffers `IntentLeave` into `chatIntents` and then quits, so `Run()` returns and the goroutine does `close(chatDone)`. `run.loop`'s `select` now has **both** `case i := <-chatIntents` (the buffered `IntentLeave`) and `case <-chatDone` (closed) ready. If it picks `chatIntents`, `case chatui.IntentLeave:` calls `chat.Println("companion: leave requested…")` — a bare blocking send on `*tea.Program`'s internal message channel with no `ctx.Done()` escape; nothing drains it once `Run()` has returned, so `loop` wedges and the `stopChat(true)` right after it never runs. Roughly 50 % per keyboard leave; `block`/`report` have the same shape (three `chat.Println` sites from Story 2.3, a fourth added by Story 2.4's send-failure notice). The `<-chatDone` arm winning is the only safe outcome and it is a coin flip. The full test suite is green because the `chatProgram` fake in `run_test.go` implements `Println` as a non-blocking capture — the seam that makes `loop` testable hides the one blocking behaviour of the real type.
- **Instance disposition:** **fix now** — elevated from the deferred list. This is a frozen-in UI hang on the epic's primary, always-visible exit control, in shipped code, against Story 2.3's own AC ("when the user triggers leave … control returns to the status line"). Fix candidate (from the logged review): track a `chatRunning` flag set when the `Run()` goroutine starts and cleared when it exits; gate every `chat.Println` / `chat.Send` on it (not on `chat != nil`), or restructure so the `<-chatDone` arm is drained before any buffered intent. Add a `run_test.go` case with a `Println` that blocks until `chatDone` is observed, to lock it.
- **Prevention:** when a test seam substitutes a fake for a real type, the fake must reproduce the real type's blocking/back-pressure contract — or a verification-gap note must state explicitly what the fake cannot catch. A green suite over a fake that is "nicer" than reality is a false signal.

#### F7 — the hub records a pairing (and relays chat) regardless of delivery success; a dropped frame is silent on both sides
- **Source:** `hub.go:253-277` — `drainQueue` does `deliver(head, m); deliver(succ, m); p.pairings[head] = succ; p.pairings[succ] = head`, recording the pairing even if either `deliver` dropped; `hub.go:242-246` — `relay` does `deliver(peer, msg)` with no success signal; `hub.go:310-315` — `deliver` is a non-blocking `select { case s.Outbound <- msg: default: }`. `deferred-work.md:179-181` (spec-2-1, edge-case + blind-hunter). Story 2.4 raised `Session.Outbound` cap 4 → 32 (`server.go:176`), which makes a real drop unlikely — it now needs the peer's handler to have stopped draining entirely, i.e. effectively gone, with its `Unregister` already inbound to tear the pairing down.
- **Detail:** for `matched` the residual risk is a recorded pairing whose peer never learned of it (it will be cleaned up on the missing peer's unregister). For the relay, a burst past the 32-frame buffer to a briefly-stalled socket loses chat lines with **no indication to either party** — the sender keeps its optimistic echo, the recipient never sees the line. `spec-2-4` Design Notes explicitly accept this for v1 ("best-effort, no ack … v1 does not ack or retry a `chat_msg`").
- **Instance disposition:** **accept as a recorded v1 deviation** — spec-sanctioned; documented here so later retros do not re-flag it.
- **Prevention / ownership:** the `deliver`-reports-success hardening (already an open deferred item, scoped to `matched` / `session_ended`) has no owner. Epic 3 owns `session_ended` reliability + the reconnect-grace resume, which is the natural home — carry the hardening into an Epic-3 story rather than leaving it unowned across another epic.

#### F8 — (low) a malformed `openers.txt` fails closed via an unrecovered goroutine panic, not a structured fatal
- **Source:** `hub.go:95` (`openers: backend.Openers()` inside `Run`), `backend/cmd/serve/main.go:40-41` (`h := hub.New(); go h.Run(hubCtx)` — fire-and-forget), `openers.go:77-88` (`Openers()` panics on a parse error), `deferred-work.md:183-185` (spec-2-2, blind-hunter + verification-gap).
- **Detail:** the behaviour is correct — fail closed, process dies — but it surfaces as a raw stack trace from a detached goroutine, and it races `srv.ListenAndServe()` on the main goroutine, so a client can briefly connect in the window before the panic propagates. The format test (`openers_test.go`) catches a bad file in CI before it can ship, so this is defence-in-depth only.
- **Instance disposition:** **defer.**
- **Prevention:** call a validate-only `backend.Openers()` in `main()` and `log.Fatal(err)` before `go h.Run(...)`, so a bad set is a one-line structured fatal at startup with nothing listening.

#### F9 — (low) the primary "leave" control is bound only to `ctrl+q`, which a tty can intercept
- **Source:** `chatui.go:167-172` — `leave: ctrl+q`, `block: ctrl+b`, `report: ctrl+r`, `send: enter`. `spec-2-5` requires the leave control ("my claude's back") to be always visible.
- **Detail:** legacy terminal flow control (`ixon`) makes `ctrl+q` (XON) / `ctrl+s` (XOFF) be swallowed by the line discipline before the program sees them, on setups that still enable it. `ctrl+c` still cleanly exits the **whole companion** via the process signal handler (`spec-2-5`), so there is an escape hatch — but not a "leave this chat, keep the companion" one. Low real-world impact for a v1 that mostly runs in a fresh tmux pane.
- **Instance disposition:** **defer / product** — add a second leave binding (e.g. `esc`) or document the caveat.
- **Prevention:** avoid the C0 codes a tty may intercept (`ctrl+q`, `ctrl+s`) for load-bearing controls when picking default keymaps.

#### F10 — pane placement was collapsed to a single tmux implementation; the non-tmux path is a dead-end hint, not another adapter
- **Source:** `spec-1-8` + `epics.md` Story 1.8 AC (`$TMUX` set → `tmux` split pane; not set → "the plugin prints exactly one line instructing the user how to open/focus the companion pane"); Epic-1 F7 (`spawn_unix.go` / `spawn_windows.go` — the no-tmux path spawns detached with `cmd.Stdin = devNull`, so `safety.Gate` reads EOF → `OutcomeDeclined` → the companion is permanently inert). `ARCHITECTURE-SPINE.md` AD-7 and the F3 capability map ("pane placement lives in the companion") name no multiplexer — tmux is a Story 1.8 implementation choice, not an architectural constraint. Raised by Diego during this retro: his terminal does native splits with no tmux, and "tmux" in the original ask was one example of "put the pane next to my session", not a requirement.
- **Detail:** tmux was the strategy that got built because it is client/server — a detached hook creates a pane with one IPC call (`tmux split-window -h companion …`), no GUI scripting. Every other environment that supports a programmatic split needs its own adapter call, and each announces itself with a distinct env var, so detection is a cheap switch: WezTerm (`$WEZTERM_PANE` → `wezterm cli split-pane`), Kitty (`$KITTY_LISTEN_ON` → `kitty @ launch`, remote control on), Zellij (`$ZELLIJ` → `zellij action new-pane`), iTerm2 (`$ITERM_SESSION_ID` → `osascript`/Python API), Windows Terminal (`$WT_SESSION` → `wt -w 0 split-pane`). The genuinely hard cases are the editor-integrated terminals (VS Code / JetBrains — no child-process split API) and native-split terminals with no CLI (Ghostty, Apple Terminal), where the honest fallback is a new OS window, not a printed hint. Epic 2 built the entire chat UX on top of this launch path, so a non-tmux first-run user reaches none of it.
- **Instance disposition:** **defer to an Epic-3 story** — a `placement` strategy registry keyed on env, with `tmux` as strategy #1, `wezterm` / `kitty` / `zellij` / `iterm2` / `wt` as cheap additions, and **"open a new OS window" as the fallback** so the first-run gate always inherits a real PTY (which also resolves Epic-1 F7's inert-companion dead end — that path only exists because there is no PTY-bearing fallback today).
- **Prevention:** an abstraction named "pane placement" that ships one concrete strategy and a `printf` for everything else is not an abstraction yet — the fallback has to be a real strategy that produces a working surface, and the retro/epic that introduces the abstraction should say which hosts it must cover (tmux, one or more native multiplexers, and a windowed fallback).
- **Progress (2026-09-08):** Diego decided F10 blocks Epic 3. First increment landed in the retro follow-ups PR: `plugin/cmd/session-start/placement.go` — an env-detected `muxStrategies` registry (`$WEZTERM_PANE`, `$ZELLIJ`, `$KITTY_LISTEN_ON`, `$WT_SESSION`), walked by `launch()` after the tmux branch and before the detached-spawn fallback; every failure still falls through to today's behaviour, so bare-terminal / editor users are unchanged. A pane placed this way has a real PTY, so F7 is resolved for WezTerm / Zellij / Kitty / Windows Terminal users. **Second increment landed (2026-09-08, `spec-epic-2-retro-item-17-windowed-placement-fallback.md`):** `plugin/cmd/session-start/windowterm.go` — the new-OS-window fallback (macOS Terminal via a self-deleting `.command` script, a probed Linux emulator, `cmd /c start` on Windows), a rung in `launch()` between the mux registry and the detached spawn, gated by `windowSupported` (`$DISPLAY` / `$WAYLAND_DISPLAY` on Linux) and the `CLAUDINGTIN_NO_WINDOW` override. This closes Epic-1 F7's inert-companion dead end for bare-terminal and editor-integrated-terminal users too — the companion now gets a real PTY there, so `safety.Gate` shows the 18+/safety screen instead of reading EOF and declining. **`epic-1-retro-item-4` retired.** iTerm2's in-place split was intentionally not built — it needs AppleScript / Apple Events, which triggers the macOS Automation (TCC) permission prompt; the new-window path covers iTerm2 users without it.
